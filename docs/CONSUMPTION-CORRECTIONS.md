# Consumption security corrections — pending review

This uncommitted change set addresses the original acknowledgement/concurrency/audit gaps and the three subsequent medium review findings. It does not establish the exact historical failure trigger, modify a historical consent, authorize a new provider operation or retry an old grant. No commit, staging, deployment or push is included.

## One authoritative consumption timestamp

Within the same `BEGIN IMMEDIATE` transaction as the conditional consumption update and event insertion, the service obtains one `consumedAt`. It requires a safe integer expiry and `consumedAt < snapshot.expires_at`; equality is expired. The SQL predicate independently requires that same timestamp to precede the stored snapshot expiry, with matching digest/consent digest and an unused approved row. Both `consumed_at` and the inserted consume event use this exact timestamp. `committed: true` is attached only after COMMIT returns.

Consumption validation reads the row without the general list/read expiry side effect. Already-expired or boundary-crossing consumption is rejected without changing consent state, clearing its digest or inserting a consume event. Expiry encountered during consumption revalidation also rejects without an expiry-driven mutation. Other invalidation rules (provider failure, changed evidence, timeout) remain fail closed. Ordinary list/read expiry transitions remain available outside the consumption attempt. Transaction failure rolls consumption, its timestamp, event and challenge invalidation back together.

The browser uses the same strict timestamp-before-expiry rule and requires event time to equal consumption time. A later response/refresh time does not redefine the transaction's acceptance timestamp.

## Exact reviewed snapshot and committed acknowledgement

The server receipt contains request ID, buyer ID, canonical consent digest, consumed state/timestamp, actual consume-event ID/type/request/time, and a server-generated correlation UUID. HTTP 200 alone is insufficient.

Server and browser import the same pure canonical serializer. Existing `synthetic-consent-v1` and legacy `paypal-consent-v1` bytes remain unchanged. New PayPal snapshots use `paypal-consent-v2`, which includes `evidence_provenance` in the ordered canonical tuple. Node and browser SHA-256 therefore bind provenance to the same challenge/consent digest as the transaction. The browser recomputes the reviewed snapshot's SHA-256, compares it to the expected digest and receipt, and checks every returned snapshot key/value, including buyer, amount/currency, merchant/name, description, order/payee/intent/status, units, nonce, revision and expiry. Missing/extra fields and inconsistent returned display totals are rejected. Object property order is not significant; array order and values are significant.

After validation, only consumption state/evidence is new: rendering retains a clone of the original reviewed snapshot. A failed or inconsistent list refresh cannot replace it or reintroduce the consume button. Accessible announcements distinguish confirmed consumption from refresh failure. An unconfirmed/failed action does not automatically retry and leaves its button disabled until an explicit local list refresh.

A receipt is a trusted same-origin server acknowledgement, not independently signed evidence against a compromised server. There is no new receipt-recovery endpoint; sequential duplicate consumption remains rejected.

## Final route and provenance corrections

`classifyRoute` is the single path classifier for admission, buyer authorization and request dispatch. It accepts origin-form ASCII canonical paths, rejects dot segments, any encoded path characters/separators, repeated slashes, trailing slash variations, fragments and malformed escaping. Extra path segments never dispatch to an action. Valid query strings remain inert metadata and cannot select the route, actor, digest or action. No URL parser normalizes a rejected path into an accepted action. Every admitted consumption request receives a correlation UUID before service entry; dispatch also asserts admission. Rejected paths cannot claim consumption, reserve a read or mutate consent.

New PayPal snapshots carry immutable, canonically bound source provenance. Only `sandboxClient` in `src/paypal-sandbox.mjs` owns the private identity registry and constructs its own frozen methods for fixed sandbox OAuth and order-read endpoints. There is no exported sealing or registration function. Other modules can only look up an existing identity; copying its fields or supplying authentication/provenance claims cannot register a client. Any explicit `transport` override is classified as mock, even a fetch reference. Unregistered injected clients can only report mock provenance. Server revalidation compares the configured adapter, fresh observation, stored binding and bound snapshot source; changed or unverifiable sources fail closed.

The read-budget integration uses validation and ledger hooks on the actual adapter rather than wrapping and rebranding a transport or arbitrary client. Reservations still precede wire requests and read-reservation diagnostics; response hooks receive sanitized status/debug metadata, order validators receive a copy, and hook return values never replace provider responses. An explicit fixture transport stays mock through the attended and read-plan layers. A native adapter identity identifies its fixed transport implementation, not successful authentication or an existing order: only successful fresh reads followed by normalization and binding create available order evidence. The trusted Node runtime and server code remain the trust boundary; this is not protection against a compromised process. SHA-256 consent binding is not a digital signature or independent proof of server identity.

Receipt validation checks source metadata against the original bound snapshot and recomputes that snapshot's canonical digest. List responses also undergo browser canonical integrity checks before rendering. Fresh observation metadata must have the same source, a valid timestamp and boolean availability; it cannot assert independently verified merchant identity. UI and audio source labels derive from the bound snapshot, with inconsistent/stale metadata preventing current-verification claims. Contradictory acknowledgement metadata does not replace the original review or announce success, even when the server already committed. Failed refresh after a valid receipt retains confirmed consumption and its validated source label.

Legacy PayPal snapshots remain byte-compatible and readable but have no canonically bound provenance, receive no new verified label, and cannot pass new consent/consumption revalidation. No historical row is migrated, re-signed, retried or rewritten. New authorized experiments would require a new v2 review; these corrections grant no provider operations.

Raw HTTP regression requests retain the exact exploit paths instead of relying on browser normalization. Separate-process coverage launches two application processes with the offline preload and a shared temporary SQLite database: the first pauses inside a mock provider, the second must reject before provider entry, then exactly one consumption event commits. The existing abandoned-claim fail-closed policy is unchanged.

## Coordination before provider reads

Live session, buyer ownership, canonical integrity, expected digest and approved consent are checked before coordination. Overlapping same-buyer/request/digest calls share the first operation's work and then reject duplicates without another revalidation. The SQLite primary key claim also prevents a separate instance sharing this database from reserving a GET. Different buyers/digests cannot join an authorized operation. No database transaction stays open during network I/O.

Atomic one-time effects, all exact provider matching and the bounded read ceilings remain unchanged. The 20-second outer timeout aborts evidence handling, invalidates still-current consent and rejects; aborted/late evidence cannot commit. The provider adapter retains its 15-second timeout. Completion and handled errors release claims by owner. Process death or cleanup failure can retain a claim, intentionally blocking future attempts. There is no lease stealing, automatic crash recovery, grant reset or retry.

## Diagnostic isolation and privacy

Only an admitted consumption request — valid Host/Origin, live buyer session, CSRF and buyer role — receives a request-specific correlation ID and attempts to record authenticated operational traces. The ID remains in response headers and committed receipts even if optional trace storage fails. Validation rejection after admission retains that correlation. Trace stages, when persisted, cover admission, validation/rejection, duplicate wait, actual bounded read reservation, provider revalidation, database processing/commit, timeout/failure and server response finish/close. Finish/close does not prove end-user delivery. No guarantee is made that every accepted request has a persisted operational trace.

`consumption_diagnostics` holds authenticated traces: default 1,000 records, 256 KiB serialized payload, seven-day age. Data is restricted to timestamp, correlation UUID, hashed local request tag, allowlisted stage/code, bounded HTTP status and event ID. No request/header/error object is serialized.

Requests rejected before admission use a separate `consumption_rejections` table. It stores only allowlisted reason counters, first/last times and bounded status, with no request ID, user, correlation or free text. Counts saturate at 2,147,483,647. Defaults are independently limited to 32 counters, 8 KiB serialized payload and one day. Unknown codes collapse to `OTHER_REJECTION`; arbitrary UUIDs cannot create additional keys. Age is based on first occurrence, so continued hostile traffic cannot indefinitely extend a counter's lifetime. Rejection writes never prune or evict authenticated traces.

Each category is pruned independently at startup, on its own writes and periodically (at most hourly). Limits describe retained records/serialized payload, not total database pages, backups or forensic erasure. These controls do not rate-limit total inbound work. Operational logging remains best effort on storage failure; authorization, validation, mandatory transactional consume events and receipt integrity are independent of optional diagnostics.

Mandatory business evidence is separate: the consent state transition, `consumed_at`, challenge invalidation and the `events` table's consume event commit in one SQLite transaction. Failure to insert that event rolls the transaction back and prevents a success receipt. Diagnostic INSERT failures are suppressed and do not bypass or substitute for any consent check. The browser confirms success only from a matching committed receipt, regardless of whether optional traces exist.

If a correlation has no operational trace, operators must treat the outcome as unknown until the canonical record, mandatory consume event and saved committed receipt can be reconciled through the existing read-only procedure. A missing trace proves neither failure nor success, and does not authorize a retry, a provider read or claim release. Preserve the response correlation if available; use the exact request/digest/event binding to examine a private read-only copy. Report NO-GO if authoritative state cannot be reconciled. Trace retention can also legitimately remove older entries. A confirmed receipt followed by a failed list refresh remains confirmed consumption with a refresh warning; an HTTP 200 without a valid receipt remains unconfirmed even when diagnostics are unavailable.

The additive claim/diagnostic/counter tables are created by `openStore` on app/store opening. Only temporary/in-memory stores are opened during this implementation; the historical private database and existing passkey credentials are not migrated or changed.

## Operator reconciliation for an abandoned claim

This is a read-only investigation procedure, not permission to recover/retry a historical order or delete a claim:

1. Stop all application instances using the affected store and retain the private attempt/claim/grant files unchanged. Establish whether the claim owner is alive; age alone cannot establish safety.
2. Inspect a private read-only copy of the request, canonical digest, consent state, consume event/receipt, claim owner/start time, grant reservations and known response outcomes. Do not export credentials, sessions, tokens or assertions.
3. If consumed state and its matching event/receipt exist, report the committed outcome without another provider request or consumption attempt. Preserve the claim until a separately reviewed housekeeping action; it cannot justify a second use.
4. If state/events disagree, a provider outcome is unknown, a read slot may have been spent, or the owner cannot be established, retain the block and report NO-GO. Do not steal the claim, replay OAuth/GET, reset a grant or edit consent evidence.
5. An unconsumed orphan is also NO-GO under the current one-shot policy. Any future recovery requires an explicitly authorized, separately reviewed reconciliation protocol proving owner termination, exact immutable binding, expiry validity and remaining external-operation budget. No such automatic release mechanism is implemented here.

## Offline tests and environment limits

Tests use isolated synthetic fixtures, in-memory/temporary databases, mock provider transports and virtual authenticators only where existing protocol tests require them. The real historical order, operator credentials and enrolled passkey are never test inputs. Full-suite security output now lives only in the temporary harness directory and is removed at cleanup; saved historical evidence is not overwritten.

The preload is a best-effort loopback-only fetch/TCP guard plus UDP-creation blocking. Browser test routes also reject nonlocal origins. It is **not an OS firewall**, does not cover every resolver/native/subprocess networking path and must not be advertised as complete network isolation. Provider operations remain injected mocks and no external service call is required. Creating an OS network namespace is unavailable in this environment; no isolation guarantee beyond the documented guards is claimed. Dependency auditing uses offline mode; it cannot establish current registry advisory status.

The regression set covers exact expiry boundaries/clock advancement/rollback, original-snapshot retention and every transaction-field mutation, canonical byte compatibility, valid receipts and post-commit refresh failure, unauthenticated flooding and independent retention, real overlapping requests with one read slot, cross-instance claims, duplicate rejection, late-response cancellation, wrong actors, provider changes and restart persistence.

## Low-severity qualification corrections

The actual fixed-endpoint constructor privately registers its own frozen methods, and any explicit transport override is always mock. The read grant and attended workflow preserve this distinction without introducing another minting authority. Hooks can reject a request or write its ledger, but cannot provide the HTTP response or replace returned order evidence. The existing v2 digest, amount/currency/payee/order checks, fixed sandbox host, persistent ceilings and cancellation remain in effect.

Correlation availability and mandatory committed business events are distinguished above from optional operational traces. New fault-injection tests deliberately deny both diagnostic categories' INSERTs, then verify committed receipt/event consistency and restart persistence. Other tests deny the mandatory event INSERT or supply an incorrect HTTP 200; neither can produce a consumption success acknowledgement. Missing traces are documented as inconclusive and never justify automatic recovery or another provider operation.
